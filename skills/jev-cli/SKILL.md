# jev-cli

`jev`コマンドでJevに評価させる。Jevは文章を生成しない。渡した*state* (テキストかJSON) を型付きの*質問*に照らして、確率を返すだけ。このskillは、依頼を質問に落とし、`jev`を実行し、返ってきた確率を読み解いて報告する。溜まった記録の集計も受け持つ。

## 前提を確かめる

評価を実行するときは1〜3を、記録を集計するだけなら1だけを行う。

1. `command -v jev`で`jev`が使えるか確かめる。無ければ止めて、`jev`が入っていないことと、jev-cliのREADMEのInstallの節で入れられることを報告する
2. `jev --help`に`JEV_CLI_OUTPUT_DIR`が出てくるか確かめる。出てこなければ、入っている`jev`は入力の記録と`JEV_CLI_OUTPUT_DIR`に対応する前の古いビルド。評価は実行できるが、出力に`request`が無く、記録も書かれない。そのことを報告の冒頭に書き、入れ直す (jev-cliのREADMEのInstallの節) よう伝えてから進む
3. `jev auth status`を実行する (キーの読み先だけを出し、値は出さない)。exit 3ならキーが見つからない。止めて、READMEのAuthenticationの節を示す。キーの値を自分で扱わない

## 質問を組み立てる

### 型を選ぶ

| 知りたいこと | 型 | criteria |
| --- | --- | --- |
| はい / いいえ | `boolean` | 省略できる。判断が割れそうなら`true` / `false`の意味を書く |
| 決まった候補のどれか | `choice` | 選択肢名 → 説明。2〜255個 |
| 段階でどのくらいか | `score` | 段階の説明を低い順に並べる。2〜10個 |

1つのstateに、答えになりうる候補が複数あるとき (二重請求とログイン不具合が同じ問い合わせに書かれている、等) は、callerが何を知りたいかで分ける。

- 1つに決めたい (「主にどれか」「どれに当たるか」) → `choice`。確率が割れたら、割れた選択肢と確率を報告に書く。stateに次点の話題もはっきり書かれているなら、候補ごとの`boolean`で聞き直せることも添える
- 当てはまるものを全部知りたい (「どれとどれが当てはまるか」「含まれているか」) → 候補ごとに`boolean`

質問名は英字か`_`で始め、英数字・`_`・`-`だけにする。

### Jevの癖を踏まえて書く

どれも、書き方を誤ると確率が意味を失う癖。

- **質問はそれぞれ独立に、並列で評価される。** 別の質問の答えを参照させても効かない (「Aで答えた方向を支持しているか」と書いても、Aの答えは見えない)。参照させたい値は、質問文に直接書き込む。どちらになるか分からないなら、両方の場合を別々の質問にして、答えを組み合わせるのは自分でやる
- **booleanどうしも独立している。** 「Xを支持しているか」と「Yを支持しているか」の確率は、足しても100%にならない。比べるなら両方を聞いて並べる。両方向を別々に聞いて組み合わせるときは、判定された方向の側の確率を答えとして使い、逆側は矛盾が無いかの確認に使う。両方とも高い、または両方とも低いときは、決められなかったとして報告する
- **criteriaの書き方が結論を決める。** 1つの選択肢だけを広い受け皿 (「それ以外」「どちらとも言えない」等) にすると、確率がそこへ寄る。選択肢の説明は、互いに同じくらいの具体さで書く
  - callerの分類に「その他」があるなら、その中身として想定されるものを具体的に並べて書く。「上のどれにも当たらないもの」のような否定の説明にはしない
  - 選択肢はcallerが挙げたものに合わせる。挙げていない選択肢 (「横ばい」「どちらでもない」等) は、stateにそれが成り立ちうるとcallerの材料から読めるときだけ足し、足したことを質問を見せるときに書く
- **答えは、質問が指している部分のstateだけで決まる。** 文章とデータを同じstateに入れて「整合しているか」を聞いても、実際には文章とデータを別々に分類した結果が返ることが多い。突き合わせたいなら、それぞれを分類する質問に分け、組み合わせは自分でやる

質問文とcriteriaは、stateと同じ言語で書く。報告は、callerの言語で書き、選択肢名はcallerの言葉に対応させる。

### stateを渡す

- テキストはそのまま`-s "..."`で、ファイルは`-s @path`で渡す (`.json`はJSONとして読まれる)
- 複数の材料は`-s key=@file`を並べ、1つのJSONにまとめて渡す。質問文からは`key`の名前で指す。JSONの一部を指すなら、keyとフィールドのパスを並べて書く (例: `the JSON under the key "market", field timeframes.1D`)
- 関係の無い情報を削り、判断に要る部分だけを渡す。stateの上限は32,000 token

### inlineか質問ファイルか

- 質問が少なく、説明に`,`も`|`も無い → inlineフラグ (`--bool` / `--choice` / `--score`)
- 説明に`,`か`|`がある、質問が多い、同じ質問を繰り返し使う → YAMLの質問ファイル (`-f`)。書式はjev-cliのREADMEのQuestion fileの節に従う。繰り返し使うものはcallerのPJに置き、1回きりのものは一時ディレクトリに置く

組み立てたら、実行の前に質問 (名前・型・質問文・criteria) をcallerに見せる。callerが既に質問の中身まで指定しているなら、見せずに実行してよい。

## 実行する

1. `--dry-run`で組み立てを確かめる (APIを呼ばず、キーも要らない)。exit 2なら、エラーの内容に沿って質問を直してもう一度`--dry-run`する
2. `--format json`を付けて本番を実行し、標準出力を一時ファイルに書いて、そこから読む。人向けの表示ではなく、jsonを読んで報告を組み立てるため

終了コードで分ける。

- **0**: 次の「読み解く」に進む
- **1** (APIエラー): 出力の全文を報告して止める。同じリクエストを繰り返し再試行しない
- **2** (使い方の誤り): 手順1に戻って直す。2回直しても通らなければ、エラーの全文を報告して止める
- **3** (認証): 「前提を確かめる」の3と同じく、READMEのAuthenticationの節を示して止める

`JEV_CLI_OUTPUT_DIR`のディレクトリが無くても、`jev`が作る。`JEV_CLI_OUTPUT_DIR`が設定されているなら、実行のあとに`ls "$JEV_CLI_OUTPUT_DIR"/*-<generationId>.json`で記録ができたかを確かめる。無ければ、報告に記録が無いことと、「前提を確かめる」の2の結果を書く

## 読み解く

jsonの`answers.<質問名>`を読む。

- **boolean**: `probability`は、その文が正しい確率。0.5付近なら決められていない。確率は答えの確かさであって、stateを正しく読んだことの保証ではない
- **choice**: `choice`は最も確率の高い選択肢。報告には、次点の選択肢とその確率も必ず書く (どこからを「割れた」と呼ぶかを決めずに済むように)。`confidence`が低い (確率が割れている) ときは、stateに答えが無いか、選択肢の分け方が合っていないことが多い
- **score**: `score`は段階の番号を確率で補間した値 (0始まり)。`probabilities`の段階ごとの分布と合わせて読む。分布が2つの段階に割れているなら、そのことも書く
- 回答が`null`なら、応答にその回答が無かった。推測で埋めない

報告には次を書く。

- 質問ごとの答えと、その根拠になった確率 (選択肢や段階の名前を添える)。ラベルだけを書いて、確率を落とさない
- 決められていない (0.5付近、確率が割れた、confidenceが低い) 質問があれば、その質問と、考えられる理由 (stateに無い / criteriaの分け方)
- 質問を分けて組み合わせた場合は、どう組み合わせたか
- `meta`の`generationId`・`inputTokens`・`marketCost`
- `JEV_CLI_OUTPUT_DIR`が設定されていれば、書かれた記録のファイル名 (`<UTCの日時>-<generationId>.json`)

## 記録を集計する

`JEV_CLI_OUTPUT_DIR`が設定されていると、評価ごとに1つのjsonが書かれている。中身は`--format json`と同じで、`request` (model・state・questions)、`answers`、`meta` (`startedAt`・`generationId`・token数・`marketCost`等) を持つ。ファイル名はUTCの開始時刻で始まるので、名前順に並べれば時系列になる。

- ディレクトリは`echo "$JEV_CLI_OUTPUT_DIR"`で確かめる。空なら、callerにパスを聞く。記録が1つも無ければ、そのことを報告して止める
- 集計には`jq`を使う。無ければ`node -e`で同じことをする
- 推移や比較を求められたら、先に質問ごと (質問文とcriteriaの組) の件数を数え、依頼に合う質問を選ぶ。推移には2件以上要る。依頼に合う候補のうち件数が最も多いものが1つに決まるならそれを選び、選ばなかった候補を報告に書く。件数が同じで決められなければ、件数を添えてcallerに選んでもらう (`AskUserQuestion`)
- 合計 (件数・token数・コスト) は、どの範囲で出したか (全部の記録か、比較した実行だけか) を報告に書く。範囲を指定されていなければ、全部の記録で出す。`marketCost`は文字列で入っているので、数にしてから足し、足したあとは、入力の値のうち小数の桁数がいちばん多いものに合わせて丸め、指数表記を使わずに書く (末尾の0は残す。例: 9桁なら`printf '%.9f\n' <和>`で`0.000045150`)
- 実行ごとのstateが違うかは、中身を出さずに確かめる (`jq -c .request.state <file> | shasum`で比べる等)
- 記録にはstateがそのまま入っている。報告にstateを写すのは、callerが中身を求めたときだけにする

よく使う形:

```sh
# 1件ずつ、時刻・質問名・答えを並べる (全体を眺める用。質問名だけで並べるので、質問文が違っても同じ名前なら同じ列に見える。推移を見るのには使わない)
jq -r '[.meta.startedAt, (.answers | to_entries | map("\(.key)=\(.value.choice // .value.score // .value.probability)") | join(" "))] | @tsv' "$JEV_CLI_OUTPUT_DIR"/*.json

# 質問ごと (名前・質問文・criteria) に件数を数える
jq -r '.request.questions | to_entries[] | [.key, .value.instructions, (.value.criteria | tojson)] | @tsv' "$JEV_CLI_OUTPUT_DIR"/*.json | sort | uniq -c

# 同じ質問 (instructionsが同じ) の答えを、実行ごとに並べる (推移を見る用)
jq -r --arg q "Is the customer asking for money back?" \
  '. as $r | .request.questions | to_entries[] | select(.value.instructions == $q) | [$r.meta.startedAt, .key, ($r.answers[.key].probability // $r.answers[.key].choice // $r.answers[.key].score)] | @tsv' \
  "$JEV_CLI_OUTPUT_DIR"/*.json

# 期間の合計のtoken数とコスト
jq -s '{runs: length, inputTokens: (map(.meta.inputTokens // 0) | add), marketCost: (map(.meta.marketCost // "0" | tonumber) | add)}' "$JEV_CLI_OUTPUT_DIR"/*.json
```

比べるときは、同じ質問 (質問文とcriteriaが同じで、`request.model`も同じ) どうしだけを比べる。質問文やcriteriaが違う実行を並べると、答えの違いがstateのせいか書き方のせいか区別できない。違いを見つけたら、どの項目 (state・質問文・criteria) が違うかも報告に書く。
